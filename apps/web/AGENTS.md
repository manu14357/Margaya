# Margaya web app guide

Folder guide for `apps/web` (React 19, Vite, TanStack Router and Query, Tailwind v4). The root [AGENTS.md](../../AGENTS.md) is canonical; this file only adds what is specific to the web app. The design system is [uiux.md](../../uiux.md).

## Where things live

- `src/routes/`: TanStack Router file routes. Signed-in screens sit under `routes/_layout/_authenticated/` (its `beforeLoad` redirects to sign-in). `src/routeTree.gen.ts` is generated by the router plugin in `vite.config.ts` and committed; never edit it by hand. Co-located `*.test.tsx` files are excluded from the route tree.
- `src/fetchers/<feature>/`: one request per file, default export, using `client` from `@margaya/libs`, throwing `HttpError` (`@/lib/http-error`) when `!response.ok`.
- `src/hooks/queries/<feature>/` and `src/hooks/mutations/<feature>/`: the TanStack Query layer. Server state reaches components only through these hooks. Streaming AI calls (`streamAi`, `src/fetchers/ai/`) are the exception.
- `src/components/<feature>/`: feature UI. `src/components/ui/`: shared primitives. `src/lib/`: pure helpers, most with a sibling `*.test.ts`. `src/store/`: zustand client-only state.
- `src/feature-registrations.ts`: feature slices (cycles, modules, intake, pages, ...) register project sections, task property slots and entity links from their own modules. A new slice adds its registration module here as a side-effect import.

Example chain, task detail page:
`routes/_layout/_authenticated/dashboard/workspace/$workspaceId/project/$projectId/task/$taskId_.tsx` (`Route.useParams()`) → `hooks/queries/task/use-get-task.ts` (`queryKey: ["task", taskId]`) → `fetchers/task/get-task.ts` → `client.task[":id"].$get(...)`, typed from the API's `AppType`.

`client` (`packages/libs/src/hono.ts`) sends cookies and an `X-Margaya-Window-Id` header. Skill: `web-data-flow`.

## Query keys and cache invalidation

- Keys are arrays whose first element is the resource: `["task", id]`, `["tasks", projectId]`, `["projects"]`, `["activities", taskId]`. Newer features use key factories (`hooks/queries/module/module-query-keys.ts`, `intake-query-keys.ts`, `page-query-keys.ts`, ...) and shared helpers (`hooks/mutations/*/invalidate-*-queries.ts`). Use the factory when one exists, and design keys so one prefix invalidation refreshes a whole feature.
- `src/query-client/index.ts` sets `refetchOnMount: false` and `refetchOnWindowFocus: false`. Data stays fresh only through mutation invalidation and realtime messages, so a mutation that skips invalidation leaves stale screens.
- The global `MutationCache` does two things to every mutation. `onMutate` optimistically patches task-query rows when the variables look like `{ id, title | status | priority | startDate | dueDate }` (`taskPatchFromVariables` in `lib/task-query/cache.ts`). `onSettled` schedules a debounced `invalidateTaskQueries`. Pass `meta: { refreshTaskQueries: false }` for mutations that cannot affect tasks.
- A 401 from any query or mutation goes through `handleUnauthorized()`. Do not add per-hook sign-out logic.

## Realtime

- `hooks/use-project-websocket.ts` (project socket, mounted by project and task layouts) and `hooks/use-user-websocket.ts` (user socket, mounted by `components/common/app-shell.tsx`) turn server messages into cache invalidations. Messages are hints, not payloads: invalidate by key, do not `setQueryData` from them.
- The API skips the initiating tab when it broadcasts (`excludeInitiatorId` in `apps/api/src/ws/index.ts`, matched by window id). The tab that made a change must refresh itself in the mutation's `onSuccess`; the socket only updates other tabs and users.
- A new message type needs a branch in the right socket hook, and a test next to it (see `use-project-websocket.test.ts`). When a project socket reopens, `catchUpProject` refetches what it covers; extend it for new project-scoped data. Skill: `realtime-events`.

## Capabilities are not authorization

- `useWorkspacePermission()` (`hooks/use-workspace-permission.ts`) asks the server through `authClient.organization.hasPermission`, so custom roles work. Gate UI with its `can*()` helpers, never with `role`, `isOwner` or `isAdmin`.
- Capabilities are `false` until loaded. Use `isCheckingPermissions` to hide actions instead of flashing them.
- A new capability goes into `CAPABILITIES` plus a helper, using the vocabulary from `@margaya/permissions`. Hiding a control is UX only: the API route must still enforce the permission. Skill: `permissions`.

## i18n

- Copy lives in `i18n/<locale>.json` at the repo root (alias `@i18n`), loaded by `src/lib/i18n/`. `i18n/en-US.json` is the source of truth. Top-level keys are namespaces: the default is `common`, others are addressed as `t("activity:...")`.
- Use static keys. `pnpm i18n:report` lists template-literal keys as dynamic calls and exits non-zero.
- Every new key needs a real translation in every locale listed in `i18n/resources.ts`, never an English copy. `pnpm i18n:check:fix` fills missing keys with the English text, and `pnpm i18n:report` then lists them as untranslated; translate them before you finish. CI runs `pnpm i18n:check`.
- Respect plural forms per locale (`_one`, `_few`, `_many`, ...); `scripts/i18n/check.mjs` validates them. Skill: `i18n`.

## Design rules (from uiux.md)

- Colour only for status, priority, area, identity and deadline. Use tokens (`bg-primary`, `text-muted-foreground`, `var(--status-started)`, `var(--priority-high)`), never raw hex in components. Tokens live in `src/index.css` and `src/styles/semantic-colors.css`.
- Every token needs a light (`:root`) and dark (`.dark`) value. The high-contrast themes add a `contrast` class on top of `light`/`dark` (`components/providers/theme-provider`) and override text tokens in `.contrast:not(.dark)` and `.dark.contrast`; add an override there when a new text token falls short. Light is the default theme. `public/theme-init.js` applies the same classes before first paint (the CSP blocks inline scripts); a change to theme names or classes must update it too, and `theme-init.test.tsx` fails if the two drift.
- Build from `src/components/ui/` primitives (`Button`, `Dialog`, `Menu`, `Badge`, ...) through props and `className` with `cn` from `@/lib/cn`. Do not restyle or fork a primitive for one screen.
- Identity colours come from `identityTileStyle` / `identityColor` in `lib/identity-color.ts`.
- Accessibility: never signal by colour alone, keep visible `focus-visible` rings, 44px touch targets on coarse pointers, respect `prefers-reduced-motion`, and design empty, loading (skeleton) and error states.

## Scripts and tests

- `pnpm --filter @margaya/web typecheck` covers both `tsconfig.app.json` and `tsconfig.node.json`.
- `pnpm --filter @margaya/web test` runs Vitest in jsdom; add a path to run one file, for example `pnpm --filter @margaya/web test src/lib/cn.test.ts`.
- Do not run `pnpm --filter @margaya/web lint`: it rewrites files.
- Tests sit beside the code. `src/test/setup.ts` only loads jest-dom, and `globals` is off, so component tests call `cleanup` in `afterEach` themselves.
- Common mocks:
  - `vi.mock("react-i18next", () => ({ useTranslation: () => ({ t: (key: string) => key }) }))`, so assertions use keys;
  - `vi.mock("@/fetchers/...")` for hook tests, which wrap a real `QueryClient` and spy on `invalidateQueries` (see `hooks/mutations/task/use-update-task-status.test.tsx`);
  - `vi.mock("@tanstack/react-router", ...)` for `useNavigate` / `useParams`, with shared state in `vi.hoisted` (see `components/nav-projects.test.tsx`).
- Browser flows live in `tests/e2e` (Playwright, `pnpm e2e`). Skills: `testing`, `local-stack`.

## Environment

- The API base URL comes from `VITE_API_URL` (default `http://localhost:1337`, see `fetchers/get-api-url.ts` and `packages/libs/src/api-url.ts`). Put local overrides in `apps/web/.env.local`.
- In the production image, `.env.production` holds `MARGAYA_*` placeholders that `env.sh` / `env.awk` replace in the built JS at container start. A new runtime-configurable variable needs both files.
