## Required variables

### General URLs

This section will cover all the variables related to the general URLs.

Name | Description |
--- | --- |
| `MARGAYA_CLIENT_URL` | The URL of the web application.
| `MARGAYA_API_URL` | The URL of the API.

The web container embeds only `MARGAYA_API_URL`, `MARGAYA_CLIENT_URL`,
`MARGAYA_TURNSTILE_SITE_KEY`, `MARGAYA_PUBLIC_SITE_URL` and `MARGAYA_SENTRY_DSN` into browser assets at startup. These values are public;
other `MARGAYA_*` variables are not substituted into frontend files. Values are
encoded as JavaScript strings. The standalone web image serves its generated MCP
discovery documents as JSON files, and no value ever enters the nginx
configuration. nginx only gets the names of the build files that carry these
values: browsers check those on every load, while other build files are cached
for a year. Configure actual public service URLs; escaping a value does not make
an invalid URL usable. Recreate the container when changing its environment.

### Database

This section will cover all the variables related to the database.

Name | Description |
--- | --- |
| `DATABASE_URL` | The full PostgreSQL connection string, in the format `postgresql://[user]:[password]@[host]:[port]/[database]`. Example: `postgresql://margaya:margaya@localhost:5432/margaya`. The user/password/database must match the `POSTGRES_*` values below.
| `POSTGRES_DB` | The name of the PostgreSQL database. Example: `margaya`.
| `POSTGRES_USER` | The username for the PostgreSQL database. Example: `margaya`.
| `POSTGRES_PASSWORD` | The password for the PostgreSQL database. Use a strong value in production.

### Authentication

This section will cover all the variables related to the authentication.

Name | Description |
--- | --- |
| `AUTH_SECRET` | Signs sessions and encrypts the SMTP passwords, OAuth client secrets, AI keys and webhook signing secrets saved in the app, so keep it stable. **Must be at least 32 characters long**. Example: use `openssl rand -base64 32` to generate a secure key in Linux/macOS. If blank, the bundled image generates one once and saves it on the uploads volume, with a startup warning if it can't; the separate API image refuses to start.
| `COOKIE_DOMAIN` | **Optional.** Domain attribute for the sign-in cookies, such as `example.com`. Leave it unset for a bundled, same-origin deployment. Set it only when the web app and API run on different subdomains of one site and both must read the session cookie. |
| `DEVICE_AUTH_CLIENT_IDS` | **Optional.** Comma-separated list of allowed device authorization client IDs. When unset, Margaya implicitly allows `margaya-cli` and `margaya-mcp` by default, so no extra configuration is required for the CLI or MCP. Override only when you need additional trusted clients, for example `margaya-cli,margaya-mcp,my-desktop-app`. |

### File storage

Without S3, Margaya keeps uploads (attachments and images in task descriptions, comments and pages) in a built-in file store on the API's disk. Files are served only through the API's authorized download route.

Name | Description | Default |
--- | --- | --- |
| `MARGAYA_STORAGE_DIR` | Folder of the built-in file store. Mount a volume here. The Docker Compose files use `/app/apps/api/data/uploads`. | `./data/uploads` |
| `MARGAYA_LOCAL_STORAGE` | `false` turns the built-in store off: uploads answer 503 until S3 is configured. | `true` |

The built-in store belongs to one machine. With several API instances, use S3-compatible storage or a volume they all share. Setting `S3_ENDPOINT` and `S3_BUCKET` switches new uploads to S3; files already stored are not moved.

### Object Storage

Margaya can use S3-compatible object storage for private uploads in task descriptions, task comments and pages, and for task exports. When it is configured, the built-in file store is not used.

MinIO is the easiest local option and the primary tested target. You can also use other S3-compatible storage backends such as AWS S3, Cloudflare R2, or [`fs`](https://github.com/ferdzo/fs).

Name | Description | Default |
--- | --- | --- |
| `S3_ENDPOINT` | The S3-compatible API endpoint used by the Margaya API for presigned uploads. Example: `http://minio:9000`. |  |
| `S3_BUCKET` | The bucket Margaya will use for uploaded files. |  |
| `S3_ACCESS_KEY_ID` | Access key used by the Margaya API to create presigned upload URLs. Optional: leave unset (together with `S3_SECRET_ACCESS_KEY`) to use the default AWS credential provider chain (IAM role / IRSA / instance profile). |  |
| `S3_SECRET_ACCESS_KEY` | Secret key used by the Margaya API to create presigned upload URLs. Must be set together with `S3_ACCESS_KEY_ID`, or left unset for IAM-role-based access. |  |
| `S3_REGION` | The storage region used for request signing. | `us-east-1` |
| `S3_PUBLIC_BASE_URL` | Optional public base URL for uploaded assets. Margaya does not require this for the current private asset flow. |  |
| `S3_FORCE_PATH_STYLE` | Use path-style S3 URLs. This should usually be `true` for MinIO and `fs`. | `true` |
| `S3_MAX_IMAGE_UPLOAD_BYTES` | Maximum allowed upload size in bytes for images and other uploaded files, with S3 or the built-in store. | `10485760` |
| `S3_KEY_PREFIX` | Optional prefix prepended to all S3 object keys. Useful for sharing a single bucket across multiple environments (e.g. `staging/`, `prod/margaya/`). Trailing slashes are trimmed automatically. |  |
| `S3_PRESIGN_TTL_SECONDS` | How long presigned upload URLs (and the built-in store's upload links) remain valid. | `300` |

### Access Control

Browser WebSocket connections require an exact origin matching `MARGAYA_CLIENT_URL`,
`MARGAYA_API_URL`, or a comma-separated `CORS_ORIGINS` entry. Wildcards, `null`, and
missing browser origins are rejected. Production deployments must configure their
public URLs. Native clients without an Origin header must provide a valid bearer
token or API key; cookies alone are not sufficient. The project and user real-time
endpoints accept only the small `{"type":"ping"}` text keepalive, with a 64-byte
message limit. The page collaboration endpoint (`/api/ws/page/{pageId}`) carries
binary document updates, so the server accepts WebSocket messages of up to 1 MiB;
larger ones close the connection before they are processed. Page sockets are also
rate limited per connection and re-check the session and page access while open.
Page collaboration works on a single instance without Redis; with Redis, instances
relay page edits and presence to each other.

The same origins guard cookie-authenticated writes. A POST, PUT, PATCH or DELETE
that carries a session cookie must come from `MARGAYA_CLIENT_URL`, `MARGAYA_API_URL`
or a `CORS_ORIGINS` entry (judged by the `Origin` header, else `Referer`, else
`Sec-Fetch-Site`); anything else gets 403 "Cross-site request refused". Calls with an
API key or Bearer token, MCP, OAuth callbacks and signed webhooks are not checked.
If people reach the web app at an address you have not listed, add it to
`CORS_ORIGINS`.

The API sends a deny-all content security policy, `X-Frame-Options: DENY` and, when
`MARGAYA_API_URL` starts with `https://`, `Strict-Transport-Security`. The web image's
nginx adds a page content security policy and HSTS for requests that arrive with
`X-Forwarded-Proto: https`. TLS itself is handled by your reverse proxy.

When set to `true`, the sign-up option will not be shown on the sign-in page and new user creation is blocked (including via SSO). **Note:** Invited password signups must present the matching invitation link. OAuth, OTP, and magic-link signups may match an invitation by email only after that email has been verified. The first non-guest user can complete initial instance setup. | `false` |
| `DISABLE_PASSWORD_REGISTRATION` | Disable local account creation through password, email OTP, magic link, and guest access. ### Proxies

Name | Description | Default |
--- | --- | --- |
| `TRUSTED_PROXIES` | Comma-separated IPs or CIDR ranges of trusted reverse proxies. Margaya first checks the actual TCP peer, then walks `X-Forwarded-For` right to left only through trusted hops. Defaults trust the bundled loopback nginx only. For a separate Docker/ingress proxy, explicitly add its IP or dedicated proxy subnet; avoid shared private-network ranges. Use `none` for direct API access without trusted proxies. Invalid entries prevent startup. `CF-Connecting-IP` and client-supplied `X-Margaya-Client-IP` are never used. | `127.0.0.0/8, ::1/128` |

<Warning>
  Only list addresses you control. Any host in this range can set `X-Forwarded-For` and have it believed, so do not include a range that clients can reach Margaya from directly. The client IP is used for rate limiting and session records.
</Warning>

### Sign-in rate limiting

Name | Description | Default |
--- | --- | --- |
| `AUTH_RATE_LIMIT_ENABLED` | Per client IP limits on the sign-in endpoints: password sign-in (10 per minute), email codes (5 sends and 10 checks per minute), magic links, password reset requests (3 per minute) and password changes (5 per minute). Other auth requests share a looser limit of 100 per 10 seconds; reading the session is never limited. An address over a limit gets HTTP 429 until its window passes. Set to `false` only for test environments that sign in many times from one address. | `true` |

<Note>
  The counts are kept in memory by each API instance: they reset when the server restarts, and with several replicas each counts on its own (Redis is not used). Behind a reverse proxy, set `TRUSTED_PROXIES` so that each client is counted by its own address; otherwise every request appears to come from the proxy and shares one limit. `MARGAYA_CLOUD=true` adds stricter limits on sign-up and invitations.
</Note>

### Web push

[Push notifications](/core/functional/account-notifications#push-notifications) are off until both keys are set. Set these on the API. The web container needs nothing.

Name | Description | Default |
--- | --- | --- |
| `VAPID_PUBLIC_KEY` | The public half of the key pair that identifies your server to push services. Browsers receive it. |  |
| `VAPID_PRIVATE_KEY` | The private half. Keep it secret. |  |
| `VAPID_SUBJECT` | A contact for push services: a `mailto:` address you read, or an `https://` URL. Some push services, Apple's among them, may refuse anything else, including an example address. | `MARGAYA_CLIENT_URL` when it starts with `https://`, otherwise the example address `mailto:admin@example.com` |

To turn push on:

1. Generate the keys once. The command prints both keys for your `.env` file, and a comment that says which contact push services will see:

   ```bash
   # Docker Compose
   docker compose exec margaya node apps/api/dist/cli/admin.js generate-push-keys

   # Running from source
   pnpm --filter @margaya/api admin generate-push-keys
   ```

2. Add `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` to `.env`. If `MARGAYA_CLIENT_URL` isn't your public `https://` address, also set `VAPID_SUBJECT` to a `mailto:` address you read. With the Helm chart, set them under `margaya.extraEnv`.
3. Recreate the container so it reads the new values, with `docker compose up -d margaya`.
4. Open **Settings** > **Account** > **Notifications**. **On this device** can now be turned on.

Things to know:

- **Push needs HTTPS.** Browsers only offer it on an HTTPS address. On iPhone and iPad, each person also has to add Margaya to their Home Screen.
- **Keep the keys stable, and back them up with `.env`.** New keys turn push off on every device until people turn it on again.
- **The API needs outbound HTTPS.** It sends each message to the push service of the person's browser, so a server without internet access can't deliver push.
- **A bad key pair turns push off.** If only one key is set or the two don't match, the API logs a warning and push stays off.
- **The API warns about a contact push services may refuse.** With push on, it logs a warning at startup while the contact is an example address such as `mailto:admin@example.com`, or isn't a `mailto:` address or an `https://` URL. Apple's push service may refuse it, and then alerts don't reach iPhone and iPad.

### Redis

Margaya supports Redis for horizontal scaling of WebSocket broadcasts. When any Redis mode is configured, multiple API instances can relay real-time updates via Redis Pub/Sub. When none are set, an in-memory adapter is used (single-instance only). Valkey works as a drop-in replacement.

Redis carries three kinds of live traffic between instances: project updates (boards, lists, cycles, pages), user updates (inbox, notifications, favorites, drafts, exports) and page co-editing (Yjs edits and presence). Run Redis whenever more than one API instance serves traffic; without it, a change made through one instance only reaches people connected to that same instance. Nothing is stored in Redis, so it needs no persistence or backups.

Redis is not used for the rest, which works the same with one or many instances:

- **Scheduled jobs** coordinate through a lease row in PostgreSQL. Two instances never run the same job at the same time, and each job claims its rows, so a reminder, digest or purge is never applied twice.
- **Instance settings** saved in the admin panel reach other instances within 10 seconds through PostgreSQL.
- **Sign-in and API key rate limits** are counted in memory by each instance, so with several instances each one allows the full limit.

Three deployment modes are supported: **Standalone**, **Sentinel**, and **Cluster**. Only one mode should be configured at a time. If multiple are set, the priority is: Cluster > Sentinel > Standalone.

### SMTP Configuration

Name | Description |
--- | --- |
| `SMTP_HOST` | The SMTP host.
| `SMTP_PORT` | The SMTP port.
| `SMTP_SECURE` | Use TLS immediately (default: `true`, typically port 465). Set to `false` for STARTTLS, typically on port 587.

| `SMTP_FROM` | The SMTP from address.

## Key points

- If you enable GitHub SSO, create a GitHub OAuth App in [GitHub Developer Settings](https://github.com/settings/developers) and set `GITHUB_OAUTH_CLIENT_ID` / `GITHUB_OAUTH_CLIENT_SECRET` (or the legacy `GITHUB_CLIENT_*` variables). See the [GitHub SSO guide](/core/social-providers/github).
- If you use the GitHub repository integration, configure a GitHub App and set the integration variables in [GitHub integration](#github-integration). See the [GitHub integration configuration](/core/integrations/github/configuration) guide.
- If you enable Google SSO, you need to set up the Google app which is used to authenticate users in the [Google Cloud Console](https://console.cloud.google.com/). See the [Google SSO guide](/core/social-providers/google).
- If you enable Discord SSO, you need to set up the Discord application which is used to authenticate users in the [Discord Developer Portal](https://discord.com/developers/applications). See the [Discord SSO guide](/core/social-providers/discord).
- If you enable Custom OAuth/OIDC, you need to configure your identity provider with the appropriate redirect URI. See the [Custom OAuth/OIDC guide](/core/social-providers/custom-oauth).
- If you have enabled SMTP, sign-in uses email verification codes by default. Set `DISABLE_EMAIL_OTP_SIGN_IN=true` to use email/password sign-in instead.
- If you need device authorization for clients beyond the defaults (`margaya-cli`, `margaya-mcp` when `DEVICE_AUTH_CLIENT_IDS` is unset), set `DEVICE_AUTH_CLIENT_IDS` to the full comma-separated list of trusted client IDs for your deployment.

## Authentication CAPTCHA

When `TURNSTILE_SECRET_KEY` is configured on the API, deploy the matching `VITE_TURNSTILE_SITE_KEY` with the web app. The API validates the token at password signup, social/OIDC initiation, guest sign-in, OTP sending (including resend), and magic-link initiation. Tokens are single-use; clients must obtain a fresh token for each attempt. OAuth callbacks and OTP redemption validate their own state/code and do not redeem the CAPTCHA token again.

The widget uses the action `auth`. The API requires that action and the exact frontend hostname from `MARGAYA_CLIENT_URL`, and rejects verification failures, redirects and timeouts. Update the API and web app together when adopting this check. Custom clients must include the token in the `x-turnstile-token` header. Automatic OIDC redirection pauses at the sign-in page when a CAPTCHA widget is configured so the user can complete it.

No secret configured means CAPTCHA is disabled, as on self-hosted instances that opt out. This does not bypass registration or guest-access restrictions.
