## Overview

Margaya uses S3-compatible object storage for uploads in:

- task descriptions
- task comments

The browser uploads directly to the configured storage backend using presigned URLs.

Margaya then serves uploaded assets back through its own API.

Current behavior:

- images render inline
- non-image files such as CSV, PDF, and ZIP render as attachment cards/links
- assets are private by default

That means one rule matters for every backend:

- `S3_ENDPOINT` must be reachable by the browser

Do not use a Docker-internal hostname such as `http://minio:9000` for a public deployment unless the browser can actually reach it.

## Required Margaya variables

```env
S3_ENDPOINT=
S3_BUCKET=
S3_ACCESS_KEY_ID=
S3_SECRET_ACCESS_KEY=
S3_REGION=us-east-1
S3_FORCE_PATH_STYLE=false
```

Notes:

- `S3_FORCE_PATH_STYLE=true` is usually needed for MinIO.
- `S3_FORCE_PATH_STYLE=false` is usually correct for AWS S3 and R2.
- `S3_PUBLIC_BASE_URL` is optional and not required for the current private asset flow.

## MinIO

MinIO is the recommended self-hosted option.

### Local Docker setup

For local development, this is fine:

```env
MINIO_ROOT_USER=margaya-local
MINIO_ROOT_PASSWORD=<choose-a-local-development-password>

S3_ENDPOINT=http://minio:9000
S3_BUCKET=margaya-uploads
S3_ACCESS_KEY_ID=margaya-local
S3_SECRET_ACCESS_KEY=<choose-a-local-development-password>
S3_REGION=us-east-1
S3_FORCE_PATH_STYLE=true
```

This works when Margaya and MinIO are on the same Docker network and your browser reaches MinIO through `localhost`.

### Public deployment

For a public deployment, expose MinIO on its own hostname through your reverse proxy.

Example:

- Margaya: `https://cloud.margaya.app`
- MinIO: `https://files.cloud.margaya.app`

This can be done with Caddy, Nginx, Traefik, or any other reverse proxy.

Then use:

```env
S3_ENDPOINT=https://files.cloud.margaya.app
S3_BUCKET=margaya-uploads
S3_ACCESS_KEY_ID=margaya
S3_SECRET_ACCESS_KEY=<generate-a-strong-random-secret>
S3_REGION=us-east-1
S3_FORCE_PATH_STYLE=true
```

You also need:

- a created bucket
- a dedicated, non-root MinIO user with access limited to that bucket
- MinIO CORS allowing your Margaya origin
- no anonymous bucket read policy is required

<Warning>
  Never expose MinIO with its default `minioadmin` root credentials. Generate
  unique credentials for every deployment and keep the MinIO Console private.
</Warning>

## AWS S3

AWS S3 is the simplest managed option.

Use a bucket and an IAM user with access to that bucket.

Example:

```env
S3_ENDPOINT=https://s3.us-east-1.amazonaws.com
S3_BUCKET=margaya-uploads
S3_ACCESS_KEY_ID=AKIA...
S3_SECRET_ACCESS_KEY=...
S3_REGION=us-east-1
S3_FORCE_PATH_STYLE=false
```

For another AWS region, adjust:

- `S3_ENDPOINT`

### Using an IAM role instead of an access key

If Margaya runs on AWS (EC2, ECS, or EKS), you can omit `S3_ACCESS_KEY_ID` and
`S3_SECRET_ACCESS_KEY` entirely and let Margaya authenticate with the instance's
IAM role. Leave both unset and the AWS SDK resolves credentials from its default
provider chain (instance profile, ECS task role, or EKS IRSA).

```env
S3_ENDPOINT=https://s3.us-east-1.amazonaws.com
S3_BUCKET=margaya-uploads
S3_REGION=us-east-1
S3_FORCE_PATH_STYLE=false
# S3_ACCESS_KEY_ID and S3_SECRET_ACCESS_KEY omitted; the IAM role is used
```

Set both keys or neither: configuring only one is rejected. The role must allow
`s3:PutObject`, `s3:GetObject`, and `s3:DeleteObject` on the bucket.

Recommended S3 CORS policy:

```json
[
  {
    "AllowedHeaders": ["*"],
    "AllowedMethods": ["GET", "PUT", "HEAD"],
    "AllowedOrigins": ["https://cloud.margaya.app"],
    "ExposeHeaders": ["ETag"]
  }
]
```

## Cloudflare R2

R2 works well because it exposes an S3-compatible API.

Use your account endpoint, bucket, and R2 access keys.

Example:

```env
S3_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
S3_BUCKET=margaya-uploads
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
S3_REGION=auto
S3_FORCE_PATH_STYLE=false
```

Notes:

- `S3_REGION=auto` is typical for R2
- a public bucket is not required for Margaya's current private asset flow

## One copy-paste self-hosted example

This example gives you Margaya + MinIO in one Compose file.

```yml
services:
  postgres:
    image: postgres:16-alpine
    env_file:
      - .env
    volumes:
      - postgres_data:/var/lib/postgresql/data
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U margaya -d margaya"]
      interval: 10s
      timeout: 5s
      retries: 5

  margaya:
    image: ghcr.io/manu14357/margaya:latest
    env_file:
      - .env
    depends_on:
      postgres:
        condition: service_healthy
    restart: unless-stopped

  minio:
    image: minio/minio:latest
    command: server /data --console-address ":9001"
    env_file:
      - .env
    volumes:
      - minio_data:/data
    restart: unless-stopped

volumes:
  postgres_data:
  minio_data:
```

Matching `.env`:

```env
MARGAYA_CLIENT_URL=https://cloud.margaya.app
MARGAYA_API_URL=https://cloud.margaya.app/api

MINIO_ROOT_USER=<generate-a-unique-admin-user>
MINIO_ROOT_PASSWORD=<generate-a-strong-random-secret>

S3_ENDPOINT=https://files.cloud.margaya.app
S3_BUCKET=margaya-uploads
S3_ACCESS_KEY_ID=<generate-a-unique-admin-user>
S3_SECRET_ACCESS_KEY=<generate-a-strong-random-secret>
S3_REGION=us-east-1
S3_FORCE_PATH_STYLE=true
```

Before testing uploads:

1. Create the `margaya-uploads` bucket.
2. Configure MinIO CORS for your Margaya origin.
3. Make sure `files.cloud.margaya.app` resolves publicly.

## Bucket lifecycle rules

Do not add an age-based expiration rule for the whole bucket: real attachments and abandoned uploads share the same keys. See [what Margaya stores and deletes](/core/installation/object-storage-and-image-uploads#what-margaya-stores-and-deletes) for the rules that are safe.

## Kubernetes (Helm)

The Helm chart sets the storage variables from `margaya.env.s3`. Keep the access key pair in a Secret, or leave `existingSecret.name` empty to use the pod's IAM role (IRSA):

```yaml
margaya:
  env:
    s3:
      endpoint: https://files.example.com
      bucket: margaya-uploads
      region: us-east-1
      forcePathStyle: true
      existingSecret:
        name: margaya-s3          # keys: access-key-id, secret-access-key
```

## Troubleshooting

If uploads fail:

- check that the bucket exists
- check that `S3_ENDPOINT` is public and browser-reachable
- check CORS on your storage backend
- check that the access key can `PutObject` and `GetObject`
