Instance administration covers settings that belong to the whole installation rather than to one workspace. Instance admins manage them in the app, without editing `.env` or restarting the server.

## Who is an instance admin

The first account created on a new instance is its instance admin. Admins can add more admins on the [Admins](#admins) page. Anonymous guests and banned accounts can't be admins.

Instance admins see an **Instance** tab in **Settings**. A person who has just been made an admin sees the tab once their browser refreshes its session, for example after they reload the page. The API checks the role on every request, so the tab is only a shortcut: non-admins who open an Instance page are sent back to their account settings.

<Info>
Instance settings are separate from workspace roles. Being an instance admin doesn't change a person's role in any workspace.
</Info>

## Where each setting comes from

Every setting has one effective value. Margaya picks it in this order, highest first:

1. **Global lock.** With `MARGAYA_LOCK_INSTANCE_SETTINGS=true`, values saved in the app are ignored and every page is read-only. A setting still takes its environment variable when one is set; otherwise it uses the default.
2. **Environment variable.** A variable that is set (present and not blank) wins over anything saved. `DISABLE_X=false` counts as set.
3. **Saved value.** What an admin saved in the app.
4. **Default.**

Next to each setting a badge shows which one is in effect:

| Badge | Meaning |
| --- | --- |
| **Default** | Nothing is set or saved. Margaya uses the built-in default. |
| **Saved here** | An admin saved the value in the app. Hover for who saved it and when. |
| **Environment: VARIABLE** | The named variable sets the value. The control is read-only. Remove the variable and restart the server to manage the setting in the app. |

<Warning>
Nothing is copied from the environment into the database. If you remove a variable and restart, the setting falls back to its saved value, or to the default if none was saved.
</Warning>

### Settings that lock as a group

- **OAuth providers.** When a provider's client ID variable is set, the whole provider (client ID and secret, plus the endpoints, scopes and PKCE for custom OAuth) comes from the environment. The provider's on/off switch has no variable, so you can always turn a provider off in the app.
- **SMTP.** When `SMTP_HOST` is set, host, port, security, username, password and From all come from the environment.

### Secrets are write-only

The SMTP password and OAuth client secrets are never shown again after saving. A secret field shows only that a value is **Saved**:

- **Replace** lets you type a new value.
- **Clear** removes the saved value.

Saved secrets are encrypted with a key derived from `AUTH_SECRET`. If you change `AUTH_SECRET`, the saved secrets can't be read any more: the field says so and you must enter them again. Left blank, `AUTH_SECRET` is generated once and saved on the uploads volume. If there's no writable volume, a startup warning says saved secrets will be lost. See [what to back up](/core/installation/backup-and-restore#what-to-back-up).

### Changes take effect quickly

A saved change applies at once on the API instance that saved it, and within 10 seconds on other API instances. Redis isn't needed for this. Each admin can make up to 30 setting changes a minute.

## General

- **Instance name** is shown on the sign-in screen and on public boards. It takes 1 to 80 characters. The default is `Margaya`.
- **Show the product landing page** decides what signed-out visitors see when they open the app's root address. When it is on (the default), they see the Margaya landing page with links to sign in and sign up. When it is off, they go straight to sign-in. Signed-in people always go to their dashboard.
- **Overview** shows the version, the number of accounts, guests, workspaces, projects and public boards, and which server services are set up: realtime (in memory or Redis), email, file storage, captcha, error reporting, cloud mode and demo mode. It never shows their values.
- **Recent delivery failures** lists workspace webhooks that used up their retries in the last 7 days, up to 20, with the workspace, webhook, event and response. The destination URL and the message body stay in the workspace's own delivery log. Email and background job errors aren't listed; they're in the server logs.

## Authentication

### Sign-up

| Switch | What it does |
| --- | --- |
| **Anyone can sign up** | When off, people need an invitation to create an account. |
| **Email sign-up** | Create accounts with an email address. Turn off to allow only single sign-on. |
| **Password sign-up for invited people** | With email sign-up off, people with a valid invitation can still create a password account. |
| **Guest access** | Let people try Margaya without an account. It also needs open sign-up and email sign-in; a note appears when it is on but inactive for that reason. |

<Screenshot src="admin/sign-up" alt="The Sign-up section with switches for Anyone can sign up, Email sign-up, Password sign-up for invited people and Guest access, each with a Default badge" caption="Sign-up switches on the Authentication page." />

<Note>
**Guest access** and the **Guests** count under **Overview** are about anonymous visitors without an account. The workspace [Guest role](/core/functional/guest-access) is separate: it belongs to a normal account limited to chosen projects.
</Note>

### Sign-in methods

Each method has a status (**Active**, **Turned off**, **Not configured** or **Needs email setup**) and a switch:

- **Email and password**
- **Email code**, a one-time code sent by email. It needs [email set up](#email).
- **GitHub**, **Google**, **Discord** and **Custom OAuth / OIDC**. A provider is active when it has credentials and its switch is on. Turning one off asks for confirmation, because people who only sign in with it won't be able to sign in.

<Warning>
The last working sign-in method can't be turned off. Its switch is disabled, and a change that would leave no way to sign in is refused.
</Warning>

<Screenshot src="admin/sign-in-methods" alt="The Sign-in methods list: Email and password marked Active, Email code marked Needs email setup, and GitHub, Google, Discord and Custom OAuth / OIDC marked Not configured with Configure buttons" caption="Each method shows its status; providers open their panel from Configure." />

### Configure an OAuth provider

Select **Configure** on a provider to open its panel:

1. Copy the **Callback URL** and add it to your OAuth app. It is `<API URL>/api/auth/callback/<provider>` for GitHub, Google and Discord, and `<API URL>/api/auth/oauth2/callback/custom` for custom OAuth. The API URL comes from `MARGAYA_API_URL`.
2. Enter the **Client ID** and **Client secret**.
3. Select **Save**.

<Screenshot src="admin/oauth-github" alt="The GitHub sign-in panel with the callback URL and a Copy button, and fields for client ID and client secret" caption="The provider panel: copy the callback URL, then enter the client ID and secret." />

For **Custom OAuth / OIDC** the panel also has:

- **Button label** (up to 40 characters), for example "Continue with Okta".
- **Discovery URL**, or the **Authorization URL**, **Token URL** and **User info URL**. Without environment variables, a custom provider counts as configured when it has a client ID, a secret, and either the discovery URL or all three endpoints.
- **Scopes**, comma separated (default `profile,email`).
- **Use PKCE** (on by default).
- **Sign in automatically**, which skips the sign-in screen and goes straight to this provider.
- **Logout URL**.

URLs must be absolute `http` or `https` URLs. For provider setup details, see [Authentication Providers](/core/social-providers/github).

### Sign-in policy

- **Allowed email domains.** New accounts must use an address at one of these domains (exact match, no subdomains), whatever way they sign up, invitations included. Margaya also refuses to invite a new address outside the list. Existing accounts are not affected. Leave it empty to allow any domain.
- **Required sign-in provider.** Everyone signs in through one provider you have set up and turned on. Other providers, passwords, email codes and magic links are refused, except that instance admins keep password sign-in (and password reset) as a way back in. Sessions that already exist keep working.
- **Require two-factor.** Accounts with a password must set up two-factor before they can do anything else. See [Require two-factor](#require-two-factor).
- **Session lifetime.** How long a session lasts without use, in hours (default 168, a week). Using a session extends it, at most once a day. New sessions use the new value.

<Screenshot src="admin/sign-in-policy" alt="The Sign-in policy section with Allowed email domains, Required sign-in provider set to No requirement, a Require two-factor switch, and Session lifetime of 168 hours" caption="Sign-in policy applies to everyone on the instance." />

### Require two-factor

Turn on **Require two-factor** under **Sign-in policy**, or set `REQUIRE_TWO_FACTOR=true` on the server, which locks the switch. It's off by default. If your own account has a password, [turn on two-factor](/core/functional/account-security#two-factor-authentication) for it first, or the change is refused. If it has no password and no sign-in provider or SAML connection that works, the change is refused too, because you could only sign in with the email codes it turns off: set a password first, with **Forgot password?** or **Reset password** on your own row under [Users](#users).

**Who it covers:** every account with a password, including one that also signs in through a provider. It leaves out:

- accounts without a password, such as those that only use a sign-in provider or SAML. They follow that provider's rules;
- anonymous guests and AI agents;
- everyone, while **Email and password** sign-in is turned off;
- everyone except instance admins, while a [required sign-in provider](#sign-in-policy) is set.

**While it's on:**

- A covered account without two-factor can only set it up. It's sent to the **Set up two-factor to continue** screen, and the API refuses everything else with 403 and the code `TWO_FACTOR_REQUIRED`. That includes the account's API keys, so its CLI and MCP tools stop too. They work again once it's set up.
- Sessions aren't ended. People already signed in are sent to the setup screen on their next request.
- Nobody can turn off their own two-factor.
- Sign-in links and codes by email are off for everyone, because they would skip the second step.

<Warning>
People who only ever signed in with an email code or link have no password, so they can't sign in at all while this is on. Their current sessions keep working until they end. To get back in, they set a password with **Forgot password?**, which needs [email](#email). Without email, select **Reset password** for them under [Users](#users) and set one. Either way, they then have to set up two-factor. The sign-in screen tells them what to do.
</Warning>

**If someone loses their authenticator and recovery codes:**

1. Another instance admin selects **Reset two-factor** for them under [Users](#users).
2. If no other admin can help, someone with shell access runs the [recovery CLI](#locked-out): `reset-two-factor <email>`.

Either way their two-factor, recovery codes and trusted devices are removed, and they're signed out everywhere. They sign in with just their password and, while the setting is on, set two-factor up again.

To turn the requirement off from the server, set `REQUIRE_TWO_FACTOR=false` and restart. That overrides a value saved in the app.

### Company sign-in and provisioning

**Company sign-in (SAML)** and **Provisioning (SCIM)** connect an identity provider, for sign-in and for adding and removing people in a workspace. See [SAML Sign-in and SCIM Provisioning](/core/social-providers/saml-and-scim).

## Email

Configure the SMTP server Margaya uses for sign-in codes, invitations and notifications. The page shows **Email is set up** once a host and a From address are set.

| Field | Notes |
| --- | --- |
| **Host** | A hostname or IP address, without a scheme or port. |
| **Port** | 1 to 65535. Leave empty for the default port of the security mode. |
| **Security** | **TLS** (usually port 465), **STARTTLS** (usually port 587) or **None** (unencrypted; use only for a local relay). |
| **Username**, **Password** | The password is a write-only secret. |
| **From** | An address, or a name and an address: `Margaya <no-reply@example.com>`. |

<Screenshot src="admin/email" alt="The Email page with the SMTP server form: host, port, security, username, password and From, plus Save changes and Send test email buttons" caption="Until a host and a From address are saved, the page shows Email isn't set up yet." />

**Remove email settings** clears the saved SMTP settings, and Margaya stops sending email until you set it up again. It appears only when there are saved settings and the environment doesn't manage email.

### Send a test email

**Send test email** is enabled once email is set up and your changes are saved, because the test uses the saved settings. Choose a recipient (your own address by default) and select **Send**. Margaya verifies the connection and credentials, then sends a short message. Admins can send up to 5 tests a minute.

If it fails, the dialog shows one of these categories. Server error text is never shown; details are in the API logs.

| Message | What to check |
| --- | --- |
| The SMTP server rejected the username or password. | Username and password. |
| Couldn't connect to the SMTP server. | Host and port. |
| The SMTP server didn't answer in time. | The server and network path. The test gives up after about 15 seconds. |
| The secure connection failed. | The security setting and the server certificate. |
| The server refused the sender address. | The From address. |
| The server refused the recipient address. | The recipient. |
| Couldn't send the test email. | Anything else: check the settings and the server logs. |

## Workspaces

- **Only instance admins can create workspaces** restricts workspace creation. Everyone else can still join workspaces they're invited to.
- **All workspaces** lists every workspace with its owner, member count, project count and creation date. Search by name or slug, use **Load more** for further pages, and select **Open** to go to a workspace.
- **Create workspace** creates one from this page.

<Screenshot src="admin/workspaces" alt="The Workspaces page with the Only instance admins can create workspaces switch and the All workspaces table listing name, owner, members, projects and creation date" caption="All workspaces on the instance, with a shortcut to open each one." />

## Public boards

- **Allow public boards.** When off, every public link answers "not found". Nothing is deleted, and turning it back on restores the boards.
- **Allow public participation.** When off, public boards are read-only: no comments, reactions, votes or requests.
- **Published boards** lists every published board with its workspace, publish date and enabled features (comments, reactions, votes, requests, guests). Search by project or workspace name. From a row you can open the board, open the project settings or **Unpublish** it. Unpublishing stops the link working until someone publishes the board again; settings, comments, reactions and votes are kept.

<Screenshot src="admin/public-boards" alt="The Public boards page with the Allow public boards and Allow public participation switches and a Published boards table showing one board with comments, reactions and votes" caption="Instance-wide switches for public boards, and every board that is published." />

## AI

AI is off until you turn it on. Under **AI**, select **Allow AI**, choose a provider and models, optionally add a local model, and decide where each kind of data may go. The page also holds the **Chat**, **Web search**, **Speech to text** and **Embeddings** settings, and **Usage across workspaces** (counts and costs only). Each workspace must then turn AI on for itself. See [AI Setup](/core/functional/ai-setup) for every setting, and [Environment variables](/core/installation/environment-variables#ai) for the `MARGAYA_AI_*` variables that lock them.

## Users

**Users** lists every account on the server (guests excepted), newest first, with its status (admin, banned, two-factor), workspace count and last activity. Search by name or email, or show only admins or banned accounts. Select a name to see the workspaces the person belongs to, their role in each, and their active sessions.

The menu on each row can:

- **Ban** an account, until you unban it or for 7 or 30 days, with an optional reason. The person is signed out everywhere at once and their API keys stop working.
- **Unban** it.
- **Reset password**: email a reset link (needs [email](#email)), or set a new password now, which signs the person out everywhere.
- **Reset two-factor**, shown for accounts with two-factor on: remove it for someone who lost their device and recovery codes, after you've checked it's really them. They're signed out everywhere and can then sign in with just their password. You can't reset your own this way.
- **Sign out everywhere**: end every session. Their API keys keep working; only the owner can revoke those.
- **Make instance admin** or **Remove instance admin**.

Banning, setting a new password, resetting two-factor and signing out everywhere also turn off [push notifications](/core/functional/account-notifications#push-notifications) on all the person's devices.

<Screenshot src="admin/users" alt="The Users page listing accounts with status, workspace count, last activity and join date, with the actions menu open on one row showing View details, Reset password, Sign out everywhere, Make instance admin and Ban" caption="The actions menu on each account. View details opens the same panel as selecting the name." />

Each of these needs a recent sign-in ([Confirm it's you](#confirm-its-you)) and is recorded in the [audit trail](#audit-trail). You can't ban yourself, and the last instance admin can't be banned or removed.

## Admins

The page lists every instance admin, and marks your own row.

- **Add admin** makes an existing account an instance admin by email. It fails if no account uses that email, or if the account is an anonymous guest or banned.
- **Remove admin** makes an admin a regular account again. They keep their account and their workspaces.

<Warning>
The last active instance admin can't be removed. The button is disabled for the only admin, and the API refuses the request.
</Warning>

<Screenshot src="admin/admins" alt="The Admins page listing an instance admin marked You with a Remove admin button, and the Audit trail below with a Recovery CLI entry that made an account an instance admin" caption="Admins and the audit trail share one page." />

### Confirm it's you

Saving instance settings, adding or removing admins, and Better Auth's account actions (`/api/auth/admin/*`: ban, remove, set a password, impersonate) need a recent sign-in. If your session started more than 10 minutes ago, Margaya asks for your password and then lets you make changes for the next 10 minutes. Admins who sign in without a password (GitHub, Google, Discord, single sign-on, email codes) select **Sign in again** instead.

An instance admin's API keys can't do any of this and only reach the workspaces the admin belongs to, unless `ALLOW_INSTANCE_ADMIN_API_KEYS=true` is set.

### Audit trail

Below the admin list, **Audit trail** shows instance changes newest first: who did it, when, and what changed. It records settings saved (which settings, never their values), admins added and removed, password confirmations, account actions from **Users** and the admin endpoints, two-factor resets, SAML and SCIM connections and the people a SCIM connection adds, deactivates or removes, and recovery CLI runs. Entries are kept for a year by default (`INSTANCE_AUDIT_LOG_RETENTION_DAYS`).

### Locked out

If no admin can sign in, someone with shell access to the server can use the recovery CLI:

```bash
docker compose exec margaya node apps/api/dist/cli/admin.js promote-admin you@example.com
docker compose exec -e MARGAYA_NEW_PASSWORD='a long new passphrase' margaya node apps/api/dist/cli/admin.js reset-password you@example.com
docker compose exec margaya node apps/api/dist/cli/admin.js reset-two-factor you@example.com
```

It also has `list-admins`, `demote-admin` (never the last admin), `unban-user` and `reset-two-factor`, which removes two-factor from an account and signs it out everywhere. Without `MARGAYA_NEW_PASSWORD`, `reset-password` prints a generated password once. On Kubernetes, run the same command with `kubectl exec` in the Margaya pod. Every run that changes an account appears in the audit trail as **Recovery CLI**.

The same CLI prints keys for web push with `generate-push-keys`. See [Web push](/core/installation/environment-variables#web-push).

## Environment variables

Setting one of these variables locks its setting in the app and shows it with an **Environment** badge.

| Setting | Variable | Notes |
| --- | --- | --- |
| Global lock | `MARGAYA_LOCK_INSTANCE_SETTINGS` | `true` makes every page read-only. |
| Instance name | `MARGAYA_INSTANCE_NAME` | |
| Show the product landing page | `MARGAYA_PUBLIC_LANDING` | `false` sends signed-out visitors straight to sign-in. |
| Anyone can sign up | `DISABLE_REGISTRATION` | `true` means invitation only. |
| Email sign-up | `DISABLE_PASSWORD_REGISTRATION` | `true` turns it off. |
| Guest access | `DISABLE_GUEST_ACCESS` | `true` turns it off. |
| Email and password sign-in | `DISABLE_LOGIN_FORM` | `true` turns it off. |
| Email code sign-in | `DISABLE_EMAIL_OTP_SIGN_IN` | `true` turns it off. |
| Require two-factor | `REQUIRE_TWO_FACTOR` | `true` turns it on. Any other value turns it off, whatever was saved. |
| Restrict workspace creation | `DISABLE_WORKSPACE_CREATION` | `true` limits it to instance admins. |
| GitHub | `GITHUB_OAUTH_CLIENT_ID`, `GITHUB_OAUTH_CLIENT_SECRET` | The older `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` also lock it. |
| Google | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | |
| Discord | `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET` | |
| Custom OAuth / OIDC | `CUSTOM_OAUTH_CLIENT_ID`, `CUSTOM_OAUTH_CLIENT_SECRET`, `CUSTOM_OAUTH_DISCOVERY_URL`, `CUSTOM_OAUTH_AUTHORIZATION_URL`, `CUSTOM_OAUTH_TOKEN_URL`, `CUSTOM_OAUTH_USER_INFO_URL`, `CUSTOM_OAUTH_SCOPES`, `CUSTOM_OAUTH_RESPONSE_TYPE`, `CUSTOM_AUTH_PKCE` | These lock as a group when `CUSTOM_OAUTH_CLIENT_ID` is set. |
| Custom OAuth automatic sign-in | `CUSTOM_OAUTH_AUTO_LOGIN` | Locks only this switch. |
| Custom OAuth logout URL | `CUSTOM_OAUTH_LOGOUT_URL` | Locks only this field. |
| SMTP | `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` | These lock as a group when `SMTP_HOST` is set. |
| Public boards | `DISABLE_PUBLIC_BOARDS` | `true` turns them off. |
| AI | `MARGAYA_AI_ENABLED`, `ANTHROPIC_API_KEY` and the other `MARGAYA_AI_*` variables | See [AI](/core/installation/environment-variables#ai). |

These settings have no variable and are always managed in the app: each provider's on/off switch, the custom OAuth button label, public participation, and SAML and SCIM connections.

For every variable, see [Environment variables](/core/installation/environment-variables).
