Margaya supports the Model Context Protocol (MCP) in two ways:

1. **Built-in HTTP endpoint**: every Margaya instance exposes `/api/mcp` out of the box. No extra setup, no extra process.
2. **Stdio package** ([`@margaya/mcp`](https://www.npmjs.com/package/@margaya/mcp)): the official Margaya MCP package on npm, a local stdio server for clients that prefer stdio transport.

Both offer the same tools for managing workspaces, projects, tasks, comments, and labels.

<Info>
This page is about Margaya as an MCP **server**: outside AI clients connect to Margaya and work in it as you. It works without Margaya's own AI features. The opposite direction is [connectors](/core/functional/ai-agents#connectors-mcp-servers): there Margaya is the MCP **client**, and Margaya's own [AI agents](/core/functional/ai-agents) use tools from outside MCP servers during their runs. Connectors need AI turned on and an agent with **Web access**.
</Info>

## Built-in HTTP endpoint

Every Margaya API instance ships with a Streamable HTTP MCP endpoint. This is the recommended approach for self-hosted deployments.

Point your MCP client at:

```
https://your-margaya-instance.com/api/mcp
```

On first connect, you will be redirected to Margaya to sign in and explicitly approve the MCP client. The page names the client and the address it will send you back to; select **Approve** only if you started the connection. After approval, all MCP tools run as your authenticated user.

<Screenshot src="mcp/consent" alt="The Margaya MCP consent page showing the client name Cursor and its local redirect URI, a warning, and Approve and Deny buttons" caption="Approve the MCP client once; its tools then act as you." />

### Use an API key instead

Clients that can't run the OAuth flow can send an API key as `Authorization: Bearer <key>` or `x-api-key`. Create one under **Settings** > **Account** > **API keys** with **Create API key**, and give it only the access the client needs (see [API keys](/core/functional/account-security#api-keys)). The key acts with its owner's permissions.

<Screenshot src="mcp/create-api-key" alt="The Create API key dialog with the name Cursor MCP filled in, an expiration choice and the access options" caption="Name the key after the client that uses it, so it is easy to revoke later." />

The endpoint implements OAuth 2.1 with PKCE for authentication. Discovery metadata is available at:

- `/.well-known/oauth-protected-resource/api/mcp`
- `/.well-known/oauth-authorization-server/api`

The endpoint serves both MCP protocol eras: modern `2026-07-28` requests are
stateless and self-contained, while 2025-era clients keep the sessionful
`initialize` flow. See [MCP 2026-07-28 stateless compatibility](/core/integrations/mcp-stateless)
for the exact contract, tests, Codex configuration, limitations, and rollback.

### Protocol compliance

Margaya follows MCP revision `2026-07-28`, the current revision as of October
2026, and keeps older clients working:

- **Version negotiation.** A modern request names its version in `_meta` and
  the `MCP-Protocol-Version` header. `server/discover` returns the supported
  versions, capabilities and server identity. An unsupported version is refused
  with `UnsupportedProtocolVersionError` (`-32022`), which lists the versions
  Margaya does support. Clients from the `2025` era still negotiate through
  `initialize`.
- **Structured output.** Every successful tool result carries its JSON both as
  `structuredContent` and as a text block, for clients that only read text. A
  list comes back as `{ "items": [...] }`. Tools with a stable shape also
  declare an `outputSchema`: `get_task`, `create_task`, `get_project`,
  `create_project`, `list_projects` and `list_project_columns`. The schemas name
  only the fields every result has, and extra fields are allowed. Errors stay
  plain text with `isError: true`.
- **Tool annotations.** Every tool has `readOnlyHint`, `destructiveHint`,
  `idempotentHint` and `openWorldHint` (always `false`, because tools act only
  on your instance). Clients can use them to ask before a destructive call.
- **Authorization.** The protected resource metadata lists
  `bearer_methods_supported`. The authorization response includes `iss`
  ([RFC 9207](https://datatracker.ietf.org/doc/html/rfc9207)), and the
  authorization server metadata advertises it. A `resource` indicator
  ([RFC 8707](https://datatracker.ietf.org/doc/html/rfc8707)) is accepted on
  the authorize and token requests. It must name one of Margaya's resources
  (`/api/mcp`, `/api/a2a` or `/api`), or the request fails with `invalid_target`.
  If the token request repeats the resource, it must name the same one as the
  authorization request. Dynamic client registration accepts `application_type`.

Some parts of the revision are not implemented yet:

- The Tasks extension for long-running operations.
- MCP Apps.
- Client ID Metadata Documents. Dynamic client registration still works.
- Audience-restricted access tokens. A token works across the whole instance
  with your permissions.
- Paginated `tools/list`. The full catalog fits in one response.

### OAuth request limits

The HTTP OAuth endpoints accept bodies up to 32 KiB and URLs up to 8 KiB.
Client registration accepts at most 10 redirect URIs. Request bodies must arrive
within five seconds. Each API process allows up to 16 concurrent requests in
each of the registration, authorization, and token endpoint groups.

Instances sharing a database also share OAuth storage and issuance limits:

| State | Stored entries | New entries per minute | Pending entries per client |
| --- | --- | --- | --- |
| Registered clients | 1,000 | 60 | — |
| Authorization requests | 10,000 | 300 | 20 |
| Authorization codes | 10,000 | 300 | 20 |

When capacity is exhausted, the endpoint returns HTTP 429 with `Retry-After`.
Clients should wait before retrying. Existing, unexpired entries are retained;
an approval that cannot issue a code leaves its authorization request available
for retry until it expires. Expired entries are cleaned up in bounded batches
when new state is created, so a previously oversized store may need multiple
attempts before accepting new entries. These limits complement reverse-proxy
connection and request limits for internet-facing installations.

## Stdio package

The `@margaya/mcp` package runs a local stdio MCP server and authenticates with Margaya using device authorization. Use this when your MCP client requires stdio transport.

### Prerequisites

- Node.js 24 or newer
- A running Margaya API
- Access to the Margaya web app to approve device login

By default, self-hosted Margaya allows both `margaya-cli` and `margaya-mcp` as device auth client IDs.

### Install and register

Use the recommended interactive installer:

```bash
npx @margaya/mcp
```

The installer lets you choose where to register the server configuration:

- Cursor (user-wide)
- Cursor (project-level)
- Claude Desktop
- Custom JSON config path

You can also run the explicit install command:

```bash
margaya-mcp install --target cursor-user -y
```

Use `--help` to see all available targets and flags:

```bash
margaya-mcp install --help
```

### Point to a self-hosted instance

When generating config, pass your Margaya base URL:

```bash
margaya-mcp install --target cursor-user -y --api-url https://margaya.example.com
```

Or set it via environment variable:

| Variable | Description |
| --- | --- |
| `MARGAYA_API_URL` | Margaya API origin. Default: `http://localhost:1337`. Do not include `/api`. |
| `MARGAYA_MCP_CLIENT_ID` | Device auth client ID. Default: `margaya-mcp`. |

If you override `MARGAYA_MCP_CLIENT_ID`, make sure it is included in [`DEVICE_AUTH_CLIENT_IDS`](/core/installation/environment-variables).

### Authentication flow

On the first tool call that needs Margaya access, the MCP server:

1. Requests a device code from Margaya
2. Prints a verification URL and user code
3. Opens the browser when possible
4. Polls until you approve sign-in
5. Stores credentials in `~/.config/margaya-mcp/credentials.json`

In the browser, check that the code matches the one in your terminal, then select **Approve**. If you open `/device` yourself, enter the code under **Connect a device** first.

<Screenshot src="mcp/device-approve" alt="The Margaya device approval page showing a device code with Approve and Deny buttons" caption="Approve the device only when the code matches the one your terminal printed." />

## Available tools

Both the HTTP endpoint and stdio package expose the same tools:

- Session: `whoami`, `list_workspaces`, `list_workspace_members`, `list_notifications`
- Search: `search`
- Projects: `list_projects`, `get_project`, `create_project`, `update_project`, `list_project_columns`
- Tasks: `list_tasks`, `get_task`, `create_task`, `update_task`, `delete_task` (moves the task to the [trash](/core/functional/trash-and-restore)), `restore_task`, `move_task`, `update_task_status`, `update_task_assignee`, `update_task_due_date`, `list_task_activity`
- Time entries: `list_task_time_entries`, `get_time_entry`, `create_time_entry`, `update_time_entry`
- Comments: `list_task_comments`, `create_task_comment`
- Labels: `list_workspace_labels`, `create_label`, `attach_label_to_task`, `detach_label_from_task`, `delete_label`
- Task relations: `create_task_relation`, `get_task_relations`, `delete_task_relation`
- Cycles: `list_cycles`, `get_cycle`, `create_cycle`, `update_cycle`, `delete_cycle`, `set_cycle_archived`, `update_cycle_tasks`, `set_task_cycle`, `transfer_cycle_tasks`
- Modules: `list_modules`, `get_module`, `create_module`, `update_module`, `delete_module`, `set_module_archived`, `list_module_tasks`, `update_module_tasks`, `set_task_modules`, `add_module_link`, `delete_module_link`
- Pages: `list_pages`, `get_page`, `create_page`, `update_page`, `replace_page_content`, `set_page_archived`, `delete_page`
- Intake: `list_intake_items`, `get_intake_item`, `submit_intake_item`, `update_intake_item`, `triage_intake_item`, `delete_intake_item`
- Task templates: `list_task_templates`, `create_task_from_template` (see [Task templates](/core/functional/task-templates))
- Repeating tasks: `get_task_recurrence`, `set_task_recurrence`, `remove_task_recurrence` (see [Repeating tasks](/core/functional/repeating-tasks))
- Automations: `list_automation_rules`, `set_automation_rule_enabled` (turning a rule on or off needs permission to update projects; see [Automate your workflow](/core/functional/automations))

`list_project_columns` is worth calling first when setting a status: the column
slugs it returns are exactly the values `create_task` and `update_task_status`
accept. Likewise `list_workspace_members` resolves the user IDs the assignee
tools expect. There is no `delete_time_entry` tool yet.

The cycle, module, page and intake tools are thin wrappers over the same API routes,
so they follow the same rules: a project with the feature turned off answers
with the API's message, and dates are calendar days (`YYYY-MM-DD`).
`triage_intake_item` checks what each action needs before calling the API.
Page content is markdown: `get_page` returns it, `replace_page_content` replaces
the whole document, and `search` also finds pages.
An API key (as `Authorization: Bearer <key>` or `x-api-key`) works on the HTTP
endpoint too, with its owner's permissions.

To hand work to Margaya from another agent instead of calling tools one by one,
see [A2A](/core/integrations/a2a).

## Debugging

To run the stdio server directly:

```bash
npx @margaya/mcp serve
```

When running from source in this monorepo:

```bash
pnpm --filter @margaya/mcp run build
pnpm --filter @margaya/mcp run start
```
