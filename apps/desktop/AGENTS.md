# Margaya Desktop guide

Folder guide for `apps/desktop` (`@margaya/desktop`), the Tauri 2 shell for Windows, macOS 14+ and Linux (WebKitGTK 4.1: Ubuntu 22.04+, Debian 12+, Fedora 38+; x86_64 and ARM64). The root [AGENTS.md](../../AGENTS.md) is canonical. Skill: `desktop-app`.

## Shape

- The app bundles only a small launcher (`src/`, React + Vite). Each server opens in its own window that loads **the server's own web UI**; the app never bundles `apps/web`.
- `src-tauri/src/`: the Rust core. `servers.rs` (server list, `servers.json` in the app config dir, ids are UUIDs), `discovery.rs` (`/api/config`, `.well-known/margaya-desktop.json`), `auth.rs` + `signin.rs` (PKCE sign-in in the system browser, deep links), `tokens.rs` (OS keychain; Secret Service on Linux), `windows.rs` (server windows: main `server-<id>`, additional `server-<id>-<n>`, sign-in popups `popup-<id>-<n>`; per-server data store, navigation, downloads, title bar, hide-on-close), `routing.rs` (pure decisions: new windows, navigation, in-app navigate script, offline backoff), `opener.rs` (every outside open on its own thread, deduped; showing a download in the file manager), `downloads.rs` (download destinations, and the in-memory ids behind `margaya://download` notification clicks), `offline.rs` (offline page), `titlebar.rs`, `bridge.rs` (`window.__MARGAYA_DESKTOP__`), `socket.rs` + `api.rs` (user socket, bearer calls, quick add), `notify.rs` (native notifications: Windows toasts with `margaya://open` click links, the notification plugin over D-Bus on Linux, one sound per notification), `sound.rs` (Margaya's notification sounds rendered to WAV and played on Windows and Linux), `notification_actions.rs` (Mark done / Snooze / Reply buttons, `margaya://notification-action`), `pause.rs` (Pause notifications), `badge.rs` + `badge_view.rs` (unread badge; on Linux the Unity launcher-entry signal and the tray label), `download_progress.rs`, `menus.rs` (tray, Recent, macOS menu), `shortcuts.rs` (global shortcuts), `launch.rs` + `jumplist.rs` (launch arguments, Windows jump list), `quick_add.rs` + `capture.rs` (quick add drafts, attachments, screenshot, clipboard, Send to), `search_window.rs`, `today_window.rs`, `files_window.rs` + `files_scope.rs` (the Files window: places, Recent, commands, the `margaya-file:` media stream, drag-out; the pure path scope, listing and search), `offline_cache.rs` (offline reading), `spellcheck.rs`, `prefs.rs` (`preferences.json`), `updates.rs` (channels, What's new), `diagnostics.rs`.
- One bundle serves the launcher (`index.html`), the quick-add window (`#quick-add`), global search (`#search`), Today (`#today`), the Files window (`#files`, lazy-loaded with the `@margaya/file-preview` renderers) and the offline page shown inside a server window (`#offline`).

## Rules

- The API is the authority. The core calls only documented API routes with `Authorization: Bearer`; it never decides permissions.
- Tokens live only in the OS keychain, one entry per server id. Never put a token, code, verifier or `webviewSecret` in `servers.json`, logs, events, URLs other than the one-time callback, or diagnostics.
- The bridge stays narrow: `startBrowserSignIn`, `openExternal` (http(s) only), `setBadge`, `showQuickAdd`, `takeHandoffSecret`, `showServers`, `signedOut`, `startSessionLink` and `finishSessionLink` (an in-window sign-in signs the app in too; the verifier and token stay in Rust), `ready({ navigate, titleBar })`, `openSignInPopup(url)`, `setSoundMuted(muted)`, `saveOfflineSnapshot(snapshot)` (plain text, validated and capped in `offline_cache.rs`), `titleBar` and `notificationSound: "system"` (static), and `window.{minimize, toggleMaximize, close, startDragging, isMaximized, onStateChange}`, which act only on the window that sent them. Server pages may call only the `bridge_message` command, granted per server at runtime (`acl.rs`: that server's windows, its exact web origin, remote pages only; never a wildcard capability), and Rust also drops any message whose page is not the server's web origin in one of that server's own windows (`server-<id>` or `server-<id>-<n>`; never a popup).
- Outside pages never open in the app because of how their URL or window looks. The only in-app outside page is a sign-in popup the page announced with `openSignInPopup`, for an OAuth request whose `redirect_uri` is this server's `/api/auth/callback/…` or `/api/auth/oauth2/callback/…`; its title is always "<site> — <server>". Outside opens are deduped (1 s) and capped at 5 per page per 10 s. No filesystem, shell or arbitrary IPC for remote pages, ever. The offline page (the app's own origin in a server window) gets only `offline_state`, `offline_retry`, `show_servers`, `offline_items` and `offline_item` (`capabilities/offline.json`, local pages only; copies of that window's own server only).
- Never open anything outside the app on the UI thread or inside a webview callback: use `opener::open_outside`. Never create a window from a main-thread handler (tray, shortcut, deep link, webview callback): hand it to `windows::spawn_ui`. The one exception is the sign-in popup, which `on_new_window` must return synchronously.
- A new command needs its name in `src-tauri/build.rs` (`COMMANDS`) and an `allow-…` entry in the right capability file.
- Each server window stays on its server's web or API origin; other links go to the system browser. Keep `disable_drag_drop_handler` (board drag and drop on Windows and Linux) and the per-server `data_directory` (Windows, Linux) / `data_store_identifier` (macOS).
- Never add a server from a deep link without the launcher's confirmation. `margaya://download` and `margaya://notification-action` links carry only an in-memory id the app handed out (plus the button); an unknown id only shows the app.
- Any window on a server's profile must pass `spellcheck::browser_args` to `additional_browser_args` on Windows: WebView2 refuses a second window on the profile with different browser arguments.
- The Files window (`files`, `capabilities/files.json`, local pages only) is the app's only file reader, and it is read-only. Every `files_*` command checks the window label and resolves each path in Rust (`files_scope.rs`): absolute, no network share, device path or `..`, then canonicalized (links and junctions followed) and inside a place the person picked with the system folder picker, or one exact file they dropped on the window. Places live in `files.json` next to `servers.json` and are granted again at start only while each still resolves where it did when picked. No capability grants `fs:`, `dialog:` or `opener:`: the dialog plugin is used from Rust only, and the fs plugin isn't registered. "Save a copy…" writes only to the save dialog's answer, never onto the source. "Open with default app" refuses files that run code (`files_scope::runs_code`). Audio and video stream through `margaya-file:` under one-time ids, answered only for the `files` webview. Dragging a file out uses the `drag` crate (an OS file drag; `e2e` builds log `drag <path>` instead). `files_window::tests::only_the_files_window_may_read_files` checks the capability files.
- CSP (`tauri.conf.json`, one policy for every bundled page): beyond `'self'`, `blob:`/`data:` images and fonts and `blob:` workers for the preview's object URLs and PDF.js worker, `'wasm-unsafe-eval'` for PDF.js's image decoders, `media-src margaya-file:` (and `http://margaya-file.localhost` on Windows) for streamed media, and `connect-src 'self' blob: data:` for the preview's own assets (PDF.js character maps, fonts, wasm). The HTML preview is a `sandbox=""` `srcdoc` frame, so it inherits this policy too.
- Quick add's page never sees file paths: attachments stay in the core under ids. Uploads `PUT` to the server's `uploadUrl` without the bearer token.
- Contract names (config fields, routes, schemes, bridge methods) are shared with `apps/api` and `apps/web`; change them on every side together.
- Linux is a shipping platform: code must compile and work there (CI runs `cargo test --locked` on Ubuntu). Gate platform APIs with `cfg(windows)`, `cfg(target_os = "macos")` and `cfg(target_os = "linux")`. Linux server windows are undecorated like Windows (bridge `platform`/`titleBar.platform` `"linux"`); the tray needs `libayatana-appindicator3`; tokens need a running Secret Service; only the AppImage updates itself (`updates::self_update_supported`, from the bundle type the bundler stamps), so a .deb or .rpm only points to the download page.
- Notifications have one sound owner: the native alert, by the server's `sound`, `soundName` and `volume` fields and this device's mute; the web app stays silent when the bridge says `notificationSound: "system"`. Windows toasts are always `<audio silent="true"/>` and the app plays the named Margaya sound itself (`sound.rs`, a port of `apps/web/src/lib/notification-sound/sounds.ts`; keep the recipes in step). Windows toast clicks are `margaya://open` links (protocol activation), never in-process `Activated` handlers. Details in the `desktop-app` skill.

## Copy

Launcher, menu, tray and notification text uses static keys under `desktop.launcher.*` in `i18n/<locale>.json`. The launcher reads them at build time through `scripts/desktop-i18n.ts`; `src-tauri/build.rs` embeds the same subtree for native menus. Every new key needs real translations in all locales (`i18n` skill). `src/lib/i18n.test.ts` fails when the launcher uses a key that has no English text.

## Commands

From `apps/desktop`:

- `pnpm test`, `pnpm typecheck`, `pnpm lint` (read-only Biome check).
- `pnpm build` builds the launcher into `dist/`; the Rust build embeds it, so build it before `cargo test`.
- `cargo test --manifest-path src-tauri/Cargo.toml`.
- Test builds: `--features e2e` writes would-be outside opens (and the Files window's `open-file`, `reveal` and `drag`) to the file named by `MARGAYA_E2E_OPEN_LOG`, takes the Files window's folder picker and save dialog answers from `MARGAYA_E2E_PICK_FOLDER` and `MARGAYA_E2E_SAVE_PATH`, (optional `MARGAYA_E2E_OPEN_DELAY_MS` simulates a slow shell) instead of opening a browser, and each native notification's click link and sound to `MARGAYA_E2E_NOTIFY_LOG`; starting the build again with that link simulates a click. Build them with another identifier (`--config '{"identifier":"com.margaya.desktop.e2e"}'`) so they get their own data directories, single-instance lock and keychain entries, and never touch an installed copy. Never ship the `e2e` feature.
- `pnpm tauri dev` (launcher dev server on port 1420), `pnpm tauri build` (NSIS + MSI on Windows, DMG + app on macOS, AppImage + .deb + .rpm on Linux). Linux builds need `libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev libssl-dev libdbus-1-dev libxdo-dev pkg-config patchelf file` (Ubuntu names). Without a Linux machine, build in Docker from `ubuntu:22.04` with those packages, `rustup` and the npm `@tauri-apps/cli`, with `APPIMAGE_EXTRACT_AND_RUN=1` (no FUSE in containers); see the `desktop-app` skill.
- Icons come from `src-tauri/icons/source.svg` (and `tray-template.svg` for the macOS menu bar); the skill says how to regenerate them. Linux installs the PNGs (32, 128, 256, 512 px) into the hicolor theme; `src-tauri/linux/margaya.desktop` is the .desktop template for the .deb and .rpm. `MARGAYA_BADGE_SAMPLES=<dir> cargo test badge` writes taskbar badge samples.
- `MARGAYA_SOUND_SAMPLES=<dir> cargo test sound` writes every notification sound as a WAV (at 70 and 100) with `levels.tsv` (peak and RMS); `MARGAYA_SOUND_PLAY=<name>[:<volume>] cargo test plays_a_sample -- --nocapture` plays one through the default output on Windows and Linux (`paplay`, `pw-play` or `aplay`).

## Updater key

`plugins.updater.pubkey` in `src-tauri/tauri.conf.json` stays a `TODO-…` placeholder in the repository; while it is, the app skips update checks. Release builds get the real public key stamped in by `desktop-release.yml` (see Releasing). Keep the private key only in CI secrets with an offline backup. Losing it strands every installed copy. Local builds with `createUpdaterArtifacts` need `TAURI_SIGNING_PRIVATE_KEY` set (a throwaway key is fine for testing; never publish such a build).

## Releasing

`.github/workflows/desktop-release.yml` builds and attaches the installers when a `v*` release is published (or by hand with a tag). A published prerelease is the Beta channel: it builds only NSIS, DMG and AppImage, copies them to the rolling `desktop-beta` release that the app's Beta channel reads, and leaves the website alone. Maintainer checklist, done once:

1. Generate the updater key pair with `pnpm --filter @margaya/desktop tauri signer generate`, with a password. Back up the private key and password offline.
2. In the repository settings, create a `desktop-release` environment with required reviewers, limited to tags.
3. Add the private key and its password as environment secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.
4. Add the public key as the environment variable `TAURI_UPDATER_PUBKEY`. The workflow stamps it into `tauri.conf.json` in the runner; the repository keeps the placeholder.
5. Optional, for a signed and notarized Mac build: `APPLE_CERTIFICATE` (base64 `.p12`), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_API_ISSUER`, `APPLE_API_KEY` (key ID) and `APPLE_API_PRIVATE_KEY` (the `.p8` contents). Without all six the Mac build is ad-hoc signed and not notarized. Windows builds are unsigned until an OV certificate is added.

The workflow fails early when the private or public updater key is missing.
